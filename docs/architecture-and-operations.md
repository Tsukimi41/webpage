# 技術選定・運用方針

最終更新: 2026-09-14  
状態: 技術構成は暫定、低コスト・静的配信方針は決定

## 1. 技術選定の評価軸

技術は流行や好みだけで決めず、次の順で評価する。

1. ブログとポートフォリオの要件を満たせるか
2. 記事を継続して追加しやすいか
3. 表示速度とアクセシビリティを保ちやすいか
4. 独自のCSSアニメーションとデザインを実装しやすいか
5. Safari、Chrome、Edge、Firefoxで段階的フォールバックを作りやすいか
6. 初期費用と継続費用を抑えられるか
7. 就職用の制作物として技術判断を説明できるか
8. 数年後に保守・移行できるか

## 2. 暫定技術構成

| 項目 | 第一候補 | 状態 | 理由 |
| --- | --- | --- | --- |
| フレームワーク | Astro | 暫定 | 静的コンテンツに強く、ブログと独自デザインを両立しやすい。必要な箇所だけJavaScriptを配信できる |
| 言語 | TypeScript | 暫定 | コンテンツ定義やコンポーネントの誤りを検出しやすく、制作物として設計品質を示せる |
| 記事 | Markdown / MDX | 暫定 | 日々の備忘録をファイルとして追加しやすく、Gitで履歴を管理できる |
| スタイル | 共通CSS＋コンポーネント単位のスタイル | 暫定 | デザイントークンと独自CSSアニメーションを明示的に管理できる |
| アニメーション | CSS中心＋最小限のJavaScript | 決定 | 表示速度、保守性、段階的フォールバックを重視するため |
| バージョン管理 | Git / GitHub | 暫定 | 更新履歴、レビュー、自動公開、就職時の提示に利用できる |
| ホスティング | Cloudflare Pages等の静的ホスティング | 暫定 | 無料枠で運用しやすく、HTTPSとCDNを利用できる |
| データベース | 使用しない | 暫定 | 初期要件では不要で、費用・障害点・保守負担を増やさないため |

## 3. Astroを第一候補とする根拠

- ポートフォリオとブログを同一プロジェクトで管理できる
- Markdown / MDXとの相性がよい
- 基本を静的HTMLとして出力できる
- アニメーションに必要な範囲だけJavaScriptを追加できる
- TypeScriptで記事メタデータやプロジェクトデータの形式を検証できる
- Reactなどの大きなクライアントランタイムをサイト全体へ配信せずに済む
- 将来、必要な箇所だけインタラクティブなコンポーネントを追加できる

### 比較対象

#### Hugo

利点:

- 高速な静的サイト生成
- ブログ運用の実績が多い
- 依存関係が比較的少ない

懸念:

- 独自のインタラクションやTypeScript中心の部品設計ではAstroより選択肢が狭くなる可能性がある

#### Next.js

利点:

- Reactエコシステムが広い
- 将来サーバー機能を追加しやすい

懸念:

- 現時点の静的ポートフォリオ・ブログには機能過多になりやすい
- JavaScript量、設定、更新対象を増やす可能性がある

正式決定前に、小さなプロトタイプと記事追加フローで妥当性を確認する。

## 4. コンテンツモデル（暫定）

### 4.1 ブログ記事

```yaml
title: 記事タイトル
description: 一覧と検索結果に表示する概要
publishedAt: 2026-09-14
updatedAt: 2026-09-14
tags:
  - TypeScript
  - Astro
draft: false
```

追加候補:

- heroImage
- series
- relatedProjects
- canonicalURL

### 4.2 プロジェクト

```yaml
title: プロジェクト名
summary: 短い概要
period: 2026
role: 自分の担当範囲
technologies:
  - TypeScript
featured: true
repository: null
demo: null
article: null
```

本文では、課題、目的、設計、担当、工夫、成果、学びを記載する。

### 4.3 タイムライン

```yaml
date: 2026-09
title: 出来事
category: project
description: 短い説明
links: []
```

分類候補は `education`, `project`, `event`, `award`, `community`, `work` とする。

## 5. 費用方針

### 決定事項

- できるだけ安く済ませる
- 静的サイトを基本にし、常時稼働する独自サーバーを持たない
- 初期リリースでは有料CMS、データベース、外部コメント基盤を導入しない
- 無料ライセンスのフォントを使用する

### 暫定的な費用構成

| 項目 | 想定 |
| --- | --- |
| ソース管理 | 無料枠 |
| ビルド・静的配信 | 無料枠 |
| HTTPS証明書 | ホスティング側の無料提供 |
| フォント | 無料ライセンス |
| データベース | 使用しない |
| 独自ドメイン | 使用する場合のみ年額費用が発生 |
| 公開用メール | 既存手段またはドメインメールの要否を別途検討 |

独自ドメインの取得先と更新価格は、ドメイン名を決めた時点で比較する。初年度の割引価格ではなく、2年目以降の更新価格を重視する。

## 6. 開発・公開フロー（暫定）

機能開発の詳細な進め方は [development-workflow.md](./development-workflow.md) に従う。

機能は小さな単位で実装し、ユーザーが意図と実物を確認した後にコミットする。一度にサイト全体を完成させる進め方は採用しない。

```text
ローカルで記事・コードを編集
        ↓
プレビューで内容を確認
        ↓
Gitへコミット
        ↓
GitHubへ反映
        ↓
自動ビルド
        ↓
静的ホスティングへ公開
```

## 7. ブログ更新方法（暫定）

1. 記事用Markdownファイルを作成する
2. タイトル、概要、日付、タグ、下書き状態を記入する
3. 本文と画像を追加する
4. ローカルプレビューで見出し、コード、リンク、画像を確認する
5. 下書き状態を解除する
6. Gitへコミットして公開する

記事投稿の負担を下げるため、将来的に記事テンプレートまたは作成コマンドを用意する。

## 8. 品質確認方針

### 公開前に毎回確認する項目

- リンク切れ
- 下書き記事の誤公開
- 本名、学籍番号、私用メール、秘密情報の混入
- 画像の代替テキストと表示サイズ
- 見出し階層
- スマートフォン幅での横スクロール
- 主要ページのキーボード操作
- `prefers-reduced-motion` 有効時の表示
- ビルド成功

### 大きなデザイン変更時に確認する環境

- Chrome / Windows
- Edge / Windows
- Firefox / Windows
- Safari / macOS
- iOS Safari
- Android Chrome

実機がない環境は自動テストやクラウドテストで補い、少なくとも最終公開前にはSafariと実スマートフォンで確認する。

## 9. 保守方針（暫定）

- コンテンツ更新と依存パッケージ更新を分けて行う
- 依存パッケージは無条件に最新版へ追従せず、変更内容と互換性を確認する
- 月1回程度、依存関係とリンク切れを確認する
- 半年に1回、プロフィール、所属、代表プロジェクト、連絡先を見直す
- 就職活動開始前に、全ページの表記、成果、公開範囲を再点検する
- Gitの履歴をバックアップとして利用する
- ドメイン更新期限をカレンダー等で管理する

## 10. Architecture Decision Record

### ADR-001: 静的サイトを基本とする

- 状態: 決定
- 理由: 表示速度、低コスト、セキュリティ、保守性を優先するため
- 結果: 初期版ではデータベース、ログイン、独自管理画面を使用しない

### ADR-002: アニメーションはCSS中心とする

- 状態: 決定
- 理由: ユーザーの表現要件を満たしつつ、JavaScript量と実行負荷を抑えるため
- 結果: 複雑な開始判定などに限って最小限のJavaScriptを使用する

### ADR-003: Astroを第一候補とする

- 状態: 暫定
- 理由: 静的ブログ、独自デザイン、TypeScript、部分的なインタラクションのバランスがよいため
- 決定条件: 記事追加、プロジェクトデータ、タイムライン、CSSアニメーションの小規模プロトタイプで問題がないこと

### ADR-004: 公開表示名はハンドルネームとする

- 状態: 決定
- 理由: 本名を伏せながら、活動実績と連絡先を一貫した名前で提示するため
- 結果: ページタイトル、著者名、構造化データ、記事署名はハンドルネームに統一する
