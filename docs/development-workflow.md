# 段階的な開発・確認・コミット方針

最終更新: 2026-09-14  
状態: 決定

## 1. 基本方針

サイト全体を一度に作らず、利用者が確認できる小さな機能単位で完成させる。

各ステップでは、単に仕様どおり動くかだけでなく、次を毎回確認する。

- 何を解決するための機能か
- 誰にとって必要か
- 本当に作りたかった体験になっているか
- 他の機能を不必要に複雑にしていないか
- 将来の拡張を妨げないか
- 削除または簡略化した方がよくないか

## 2. 1ステップの進め方

```text
1. 目的を1文で定義する
        ↓
2. 今回作る範囲と作らない範囲を決める
        ↓
3. 受入条件を決める
        ↓
4. 最小の実装を行う
        ↓
5. ビルド・動作・表示を確認する
        ↓
6. ユーザーが実物を確認する
        ↓
7. 「本当に欲しかったものか」を見直す
        ↓
8. 必要なら同じステップ内で修正する
        ↓
9. 合意できた状態をコミットする
        ↓
10. 次の1ステップを選ぶ
```

## 3. ステップ開始時に明文化する項目

各ステップの着手前に、最低限次を短く記録する。

```markdown
## Step N: 機能名

- 目的:
- 対象ユーザー:
- 今回作るもの:
- 今回作らないもの:
- 受入条件:
- 関連する既存機能:
- 将来の拡張候補:
```

## 4. ステップ完了時の確認

### 4.1 目的への適合

- 当初の目的を達成しているか
- 訪問者が説明なしでも用途を理解できるか
- 採用担当者または技術者にとって有益か
- 見た目の楽しさが、情報理解を妨げていないか

### 4.2 品質

- 対象画面幅でレイアウトが破綻しないか
- キーボードとタッチで操作できるか
- Safari、Chrome、Edge、Firefoxで成立する設計か
- 動きを減らす設定でも利用できるか
- 不要なJavaScriptや重い画像を追加していないか
- エラー、警告、リンク切れがないか

### 4.3 拡張性

- データと表示を必要な範囲で分離できているか
- 同種の項目を後から追加しやすいか
- まだ必要でない抽象化や設定を作っていないか
- 将来候補を先回りして実装していないか

## 5. コミット方針

### 決定事項

- 原則として1ステップにつき1つ以上の独立したコミットを作る
- 動作しない途中状態を完成コミットとして扱わない
- ユーザーが確認し、意図に合うと判断した状態をコミットする
- 無関係な変更を同じコミットへ混ぜない
- ドキュメントと実装の内容が食い違う場合は、同じステップで更新する
- 秘密情報、私用メール、認証情報、生成物の不要なキャッシュをコミットしない

### コミットメッセージ

Conventional Commitsを参考に、変更の目的が分かる短い形式を使う。

```text
feat: add portfolio hero summary
feat: add project card component
feat: add timeline data model
style: add reduced-motion transitions
docs: record portfolio requirements
fix: prevent mobile timeline overflow
refactor: separate project data from presentation
```

日本語のコミットメッセージを使う場合も、同じ粒度を保つ。

```text
feat: トップに自己紹介と注力分野を追加
fix: モバイルで年表がはみ出す問題を修正
docs: アニメーションの受入条件を更新
```

## 6. 完了の定義

ステップは、次をすべて満たしたときに完了とする。

- 目的、範囲、受入条件が記録されている
- 実装が受入条件を満たしている
- 必要な確認が終わっている
- ユーザーが実物または確認結果を見ている
- 「本当に欲しかったものか」をユーザーと確認している
- 関連ドキュメントが更新されている
- 秘密情報や意図しないファイルが含まれていない
- 合意した状態がコミットされている

## 7. 変更・撤回の扱い

- 一度決めた機能でも、目的に合わなければ変更または削除する
- コミットは決定を固定するものではなく、安全に比較・撤回するための記録として使う
- 大きな方向変更は、新しいADRに理由と影響を記録する
- 実装後に得た知見が要件を変える場合は、要件文書を更新してから次へ進む
- 将来機能は実装せず、候補として文書に残す

## 8. 最初の開発ステップ候補

以下は順序の候補であり、各ステップ開始前に改めて必要性を確認する。

1. プロジェクト基盤と空のトップページ
2. 色・書体・余白の最小デザイントークン
3. トップページの自己紹介領域
4. 代表プロジェクト1件の表示
5. プロジェクトを追加できるデータ構造
6. 技術スキルと根拠の関連付け
7. 年表の静的表示
8. 年表の控えめなスクロール演出
9. ブログ記事1件の表示
10. 記事一覧、タグ、読了時間
11. ナビゲーションと各画面の統合
12. 対象ブラウザ・端末・アクセシビリティの総合確認

アニメーションは、静的な情報構造が成立した後に追加する。これにより、動きがない状態でも内容が伝わることを確認できる。

## 9. 各ステップの記録場所

実際のステップ記録は、実装開始時に `docs/steps/` 配下へ追加する。

例:

```text
docs/steps/
├─ 000-project-foundation.md
├─ 001-design-tokens.md
├─ 002-home-introduction.md
└─ 003-first-project.md
```

各記録には、目的、範囲、受入条件、確認結果、ユーザーフィードバック、関連コミットを残す。
